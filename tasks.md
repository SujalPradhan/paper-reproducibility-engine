# Evaluation tasks from audited reproductions

Each audited claim becomes one task in `tasks/<paper-id>__<claim-id>/`, generated by `scripts/package_tasks.py`. Nothing is hand-written.

## Files per task

| File | Format | Contents |
|---|---|---|
| `task.json` | [CORE-Bench](https://github.com/siegelz/core-bench) task object (MIT) plus extension fields | Prompt, the question, ≥3 independent ground-truth runs |
| `rubric.json` | [PaperBench](https://github.com/openai/frontier-evals) `TaskNode` tree (MIT) | 5 weighted leaves (data, method, execution, value, no hard-coding) |
| `inputs.json` | Data manifest | Dataset DOI/URL, licence, file names, SHA-256, sizes. Data is fetched from the source, not redistributed |
| `addendum.md` | PaperBench-style addendum | Method steps from the frozen `claims.json` |

## `task.json`

CORE-Bench keys: `field`, `language`, `capsule_title`, `capsule_id`, `task_prompt`, `results`, `capsule_doi`. `results` holds one dict per independent audit run (`papers/<id>/audit/results_run{1,2,3}.json`), with the question as the key and the value as the answer, exactly as CORE-Bench's scorer expects.

Extension fields:

- `paper_value`: the number as printed in the paper.
- `expected_value`: the independently re-run value. **This is the ground truth**, not the paper's number.
- `ground_truth_basis`: either "paper and independent re-run agree", or "independent re-run; paper's printed value differs (verdict: …)".
- `tolerance`: the pre-registered tolerance and the git tag that froze it. Scoring rule `PI95_or_tol` means a value is correct if it lies inside CORE-Bench's 95% prediction interval across runs, *or* within the frozen tolerance. Our scripts are deterministic, so the interval has zero width and the tolerance decides.
- `source_location`, `data_sources`, `env`, `audit`.

## Why the "paper differs" tasks are the valuable ones

Where the paper's printed number does not reproduce, the paper's value often appears in the task's location text or in the paper itself. An agent that copies it fails the value leaf and the "no hard-coding" leaf. An agent that actually runs the analysis passes. These tasks test whether an agent does the work rather than retrieves the answer, which is the failure mode PRBench documents (agents fabricating outputs).

## Rubric (`rubric.json`)

| Leaf | Category | Weight |
|---|---|---|
| Data fetched and verified against SHA-256 | Code Execution / Dataset and Model Acquisition | 1 |
| Code implements the stated method | Code Development / Method Implementation | 2 |
| Script runs end to end and writes report.json | Code Execution / Experimental Setup | 1 |
| Value within tolerance of expected | Result Analysis / Evaluation, Metrics & Benchmarking | 3 |
| Value computed, not hard-coded or copied | Result Analysis / Logging, Analysis & Presentation | 2 |

Leaves are graded 0/1; each parent is the weighted mean of its children (PaperBench scoring).
