Do Wiley papers reproduce?

We took 4 open-access Wiley papers, downloaded their public data, and re-ran the analyses without the authors' help. Every headline number was compared against a tolerance we committed to git before running anything.

Show as a table

Reproducibility is not a yes-or-no property of a paper. Within a single paper, some numbers came back to the last printed digit and others did not. The useful output is the claim-level table, not a badge.

When a number misses, the paper usually tells you why, if you read closely. In the papers that did not fully reproduce, the reviewers found inconsistencies inside the papers themselves: sample sizes printed differently in different places, standard errors that cannot produce the printed p-values, and Discussion sections that contradict their own tables. These are exactly the signals an editor would want before publication.

The method is the product, not the verdict count. 4 papers is not a rate, and we picked papers we expected to be tractable. What carries over is the pipeline: claims frozen in git before analysis, scripted re-runs from the original repositories, and an independent auditor who re-ran everything from a clean checkout.

Methods and evidence

  1. Screen. Search Europe PMC for open-access Wiley papers, read each data availability statement, and check the article licence (CC BY only), the data licence and a real anonymous download.
  2. Pre-register. An extractor agent reads the full text and writes claims.json: each headline number exactly as printed, its location, the method steps, the ambiguities and a tolerance. The lead commits it and tags it claims-frozen-<paper> before any analysis runs.
  3. Reproduce. A separate agent runs the authors' code unchanged where it exists, otherwise writes one clean script from the methods. The script itself writes results.json. Every assumption is logged before results are seen; any later change is marked POST-HOC.
  4. Compare. compare.py applies fixed rules (below) to the frozen claims and the script's output. No human or agent picks the verdict.
  5. Audit. A fresh agent that saw none of the above clones the repository, re-downloads the data from the original source, checks the checksums, re-runs the script three times, cross-checks key numbers with a different implementation, and can override a verdict only with a written reason.
  6. Package. Each audited claim becomes an evaluation task in the CORE-Bench format, with a PaperBench-style rubric, for AI-lab evaluation sets.

Verdict rules (fixed before any reproduction ran)

  • ✓ Reproduced Our value is within the pre-registered tolerance of the paper's printed value.
  • ≈ Partial Outside tolerance, but the same direction, the same significance conclusion and within half the paper's magnitude.
  • ✗ Not reproduced Computed, but the direction, the significance conclusion or the magnitude differs beyond that.
  • – Not reproducible The value could not be computed from the deposited data and the stated methods.

Notes

  1. Papers were chosen for tractability (open data, CC BY licence, analysis runnable in R or Python in under an hour), so these results do not estimate a reproducibility rate for any journal.
  2. Dryad, the most common data repository for Wiley ecology papers, blocks anonymous file downloads (HTTP 401) as of 20 October 2026. Machine access needs an API token.
  3. Verdicts are produced by scripts/compare.py; its rules and unit tests were committed before any reproduction ran.
  4. Article text was retrieved as JATS XML from Europe PMC. Wiley Online Library blocks scripted access.
  5. Prior art: CODECHECK, ReScience C, the Institute for Replication, the Odum Institute (AJPS) and SEER-Repro (arXiv 2610.23845) have reproduced some Wiley papers. None covers Wiley's ecology and health portfolio systematically. See landscape.md.
  6. Limitation we found in our own process: the claims freeze is verifiable in git, but the reproducers' statement that each assumption was logged before results were seen is self-reported (code, log and outputs were committed together). The next version commits the analysis plan before the first run.
